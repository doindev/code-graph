# MCP session activity and private approval delivery

HTTP MCP sessions have a one-hour **idle** timeout. Accepted authenticated requests renew the deadline, and active POST responses hold a lease through synchronous and asynchronous completion. Parallel calls share the same ID and lease count. An idle SSE GET does not keep a session alive indefinitely. Identity checks precede renewal; deletion and expiration cannot be undone by late response completion. DBA session grants and editor pairings use the same lifetime.

Unknown, expired, deleted, and pre-restart session IDs return HTTP 404. The client must initialize a fresh session without the old header. The session-based [MCP transport specification](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/basic/transports.mdx) requires this behavior and does not require clients to adopt replacement IDs from ordinary responses. The server does not rotate IDs or alias terminated sessions. Clients which repeatedly send an expired ID must reconnect or fix their recovery logic; keep-alive calls cannot recover a terminated session.

Human authorization remains enforced and audited. Native and browser reviewers see the full request, choices, target, deadline, and execution details. MCP callers receive an asynchronous operation with `operationId` and `state: queued`, without approval-delivery details or choices. Use `dba_request_status` and `dba_cancel_request` with `operationId`; `approvalId` and the old status-only `requestId` remain accepted aliases. Submission `requestId` remains a separate idempotency key. Status polling never repeats the database operation or resets its deadline.

Queued operations need no agent-side intervention. Continue polling until `complete`, `paired`, `failed`, or `cancelled`; a running operation can include its execution `job` and `jobId`. Existing permissions can submit work immediately. Denial returns a failed MCP tool result with `error.code: approval_denied`; expiry while waiting returns `approval_timeout`. Session/access loss and execution failures remain separate errors. Approval waits do not occupy database worker slots or hold an HTTP call open beyond a client's request timeout. Execution cancellation and result release retain their existing behavior.

In `/dba`, open the workspace settings gear, choose **RAM**, and set **Agent approval timeout (seconds)**. The default is **300 seconds (five minutes)**, with a range of **10–3600 seconds**. The browser writes `approval-settings.json` atomically in the configured DBA data directory; restart reloads it. SQL, connection/binding/native operations, and editor collaboration all use this limit. New requests capture the configured deadline; changing it does not extend or shorten requests already waiting. Invalid saved settings fall back to five minutes with a warning in settings telemetry. Query timeouts and SQL error-decision timeouts remain separate.

The existing pending-request and retained-result limits still apply. Neither a timeout, a late approval, a duplicate submission, nor a new MCP session automatically replays a database operation. Clients should refresh their tool definitions after upgrading the server.
