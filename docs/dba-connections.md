# DBA connection setup

DBA remains opt-in (`--dba`); `/dba` uses the configured UI port. The graph/admin startup
flags are unchanged. Browser access is automatic and local-only; it is not local-user
authentication. MCP agent authentication remains required; grants now also bind the connection name as described below.

## Workflow

1. Add a connection and choose from the [41 named JDBC templates](dba-grid-and-drivers.md),
   or Custom (always last). Search and arrow-key navigation
   work in the locally bundled icon grid. Custom starts with connection values blank.
2. Named templates check release metadata through the configured downloader (embedded Central
   or installed Maven with corporate settings). A verified current installed bundle
   is reused; otherwise choose Download latest via Maven, Browse, Cancel, or an explicitly
   selected cached bundle. An unavailable latest-version check is labelled unavailable,
   with sanitized failure details and Retry. Configure **Settings → Driver downloads**;
   see [corporate mirrors, settings.xml, CA PEM and optional TLS bypass](dba-driver-downloads.md).
3. Configure General, Driver, Authentication & TLS, Network, Driver properties, and Pool &
   lifecycle. The dialog is resizable. General can generate a URL or use an explicit URL.
   Advanced discovery is explicit/lazy and uses the selected driver’s `getPropertyInfo`.
   JDBC descriptors can be incomplete; arbitrary overrides remain available. Driver defaults
   are informational, not saved overrides. Unknown properties are write-only secrets.
4. Test the draft. Nothing is saved. Success opens a modal with database/driver versions,
   elapsed time, the vendor version query and its bounded tabular result. Failure opens a
   modal with validation stage, exception types, SQL state/vendor code where available,
   and corrective guidance. Raw driver exception messages are withheld because they can
   contain credentials. A version-query permission failure is distinguished from login failure.
5. Save after a successful unchanged test, use Test & Save, or explicitly confirm Save untested.
   Untested save still checks required settings, key validity, driver loading and vault access.
   Failed tests preserve the draft. Test data/history is **never written to disk**.

Test success uses an opaque, browser-session-bound receipt in memory only (10-minute expiry,
32-entry bound). Changed settings, secrets, driver bytes, or key bytes invalidate it.
Test responses/results expire with ordinary jobs and the UI releases them after display.
Custom drivers with no recognized database product show JDBC version metadata instead of
guessing executable SQL. Embedded database tests require confirmation because drivers can
create files or run configured initialization SQL. Only fixed read-only version SQL is
generated by the application; arbitrary JDBC drivers are trusted executable code, not sandboxed.

## Editing saved connections

**Edit Connection** in the connection tree restores saved values across General, Driver,
Authentication & TLS, Network, Driver properties, and Pool & lifecycle, including native
MongoDB/Redis options. Saved secrets stay write-only and are retained unless replaced or
removed. Driver coordinates/classpaths, explicit properties, pool overrides, and access
settings are preserved when saving an edit.

In **Edit URL** mode, address fields display the saved JDBC URL's host, port, and database
or service. Options defined in that URL appear on their property tabs with a **JDBC URL**
indicator; edit those values on General. **Generate from fields** retains URL options,
including TLS settings. Advanced descriptors and multiple-host URLs remain available in
Edit URL mode, with no invented address defaults. New connections still use template defaults.

Validation (2026-09-24): the dedicated browser suite passed all six tabs, 13 JDBC URL
forms, native MongoDB/Redis settings, mode changes, option preservation, and save/reopen.
The broader core browser run reached an unrelated grid-drag assertion failure; a run
with the unchanged connection editor also failed earlier on an editor-focus assertion.
Those broader browser checks are not reported as passing.


## Script files and execution targets

The connection tree displays an expand/collapse chevron, database icon, connection name,
and italic host/port (or a local/in-memory label). Addresses truncate while the right-edge
ellipsis remains visible. The menu offers SQL Editor → Open SQL script, Last edited SQL script,
and New SQL script; Edit Connection; Connect; Invalidate/Reconnect; Disconnect; and Refresh.
Copy, Delete, and Rename appear above Refresh. Root Delete confirms removal of the saved
connection, never the database; Rename changes the connection label only. Last edited selects the most recently
edited open Script for that connection, including restored tabs in the same browser session.
New/Open use the menu's connection without retargeting existing scripts.

Connect opens and verifies a pooled connection asynchronously. Reconnect closes the old pool
and opens a fresh connection. Disconnect closes the pool while retaining the saved profile
and scripts. These operations are disabled while that connection has queued/running jobs.
Connected state means the pool currently has physical connections; it does not continuously
probe database reachability. Later SQL execution or metadata browsing can reconnect lazily.
Expanding a root loads schemas; Refresh reloads expanded metadata or updates a collapsed root's
state without connecting it. Menu states are refreshed from the backend when opened.

The compact 36-pixel full-width workspace toolbar sits above both the connection tree and
script tabs. Branding and the open-in-new-tab link appear at its left, retaining the former
header background. Its File group contains 30-pixel icon-only New/Open/Save/Save As buttons
with tooltips. A right-aligned settings gear opens **RAM** and **Agent access**; the menu
supports keyboard navigation, Escape, outside-click dismissal and focus restoration.
There is no separate page header, status banner or End session button. Save and
Save As apply to the active script, including when a different tab was saved previously.
Each script has a compact 38-pixel vertical rail beside its editor. The 30-pixel icon-only
Run SQL/Explain/Cancel controls remain at the top. A bottom group contains Settings, an
ellipsis separator, and per-Script Server output, Execution log and SQL variables placeholder
toggles. The placeholders start off, retain session-scoped state for their Script tab, and do
not alter panels yet. A short editor scrolls the rail vertically instead of overlapping its
controls. There is no horizontal toolbar inside a script. DDL controls have been removed from the UI;
the existing catalog APIs and MCP tools remain available.

A line-number gutter sits between the execution rail and SQL text. It tracks edits, opened
files and tab changes, and stays aligned during vertical scrolling and editor resizing.
Only visible line numbers are rendered, including blank/trailing lines. SQL does not wrap:
long lines scroll horizontally while the gutter stays fixed.

Each tab displays its own connection name as a compact, caret-free, clickable and
keyboard-accessible dropdown. When closed it is only as wide as the selected display name.
The native dropdown may expand for its choices; names are capped at 50 displayed characters
plus an ellipsis while the full name remains available to accessibility and tooltip text.
Changing that selector affects only that tab, activates it, and clears its previous results.
It is disabled while the tab has a running/submitting job. The last connection selected
in the tree or a tab is the default for new/opened scripts; other existing tabs never
silently change targets. Removing a connection leaves its tabs disconnected and execution
disabled rather than falling back to another connection. New/Open remain available with
no connections; Save/Save As are disabled when there is no active script.

Open accepts UTF-8 `.sql`/`.txt` files up to 1 MiB and does not execute them. Where supported,
the browser’s native File System Access picker keeps a file handle for subsequent Save;
Save As prompts for another destination. Other browsers use file selection plus downloaded
copies, with an explicit warning that they cannot overwrite the original file. Script text
is not placed in browser local storage or server configuration. While the same browser session
remains active, the backend keeps a memory-only workspace snapshot. Refreshing restores up to
12 tabs in their current order, each tab's unsaved text, title, connection target, dirty state,
output toggles and editor/output divider position, plus the active tab and editor focus. Changes
are debounced and periodically synchronized. Query results, job state and browser file handles
are deliberately excluded; a restored file therefore requires Save As (or a newly selected
handle) before it can overwrite a file. Ending or expiring the session, or stopping the server,
destroys the snapshot. Dirty markers, close/session confirmation and a page-unload warning
protect unsaved changes. Maximum 12 tabs and 1 MiB of UTF-8 text per tab.

Shortcuts: Ctrl/Cmd+O Open, Ctrl/Cmd+S Save, Ctrl/Cmd+Shift+S Save As, Ctrl/Cmd+Alt+N New,
Ctrl/Cmd+Enter Run, Ctrl/Cmd+/ toggle comments. Tab inserts a literal tab at the cursor. With
one or more lines selected, Tab indents every selected line and Shift+Tab outdents them without
deleting or collapsing the selection. Editor focus is retained; Ctrl/Cmd+Tab remains available
for navigation.

Run sends selected SQL, or the entire editor, to JDBC without the agent SQL allowlist.
Human DDL, DML, functions, procedural blocks and driver-supported scripts execute with the
database account's privileges. No SQL-type or affected-row permission limit is imposed on
humans; input, concurrency, timeout and result-retention limits still apply. Client-only
commands (such as psql backslash commands or COPY STDIN streaming) are not a JDBC SQL interface.

Default execution uses a transaction and commits after successful execution/result collection.
Failure or cancellation requests rollback, but vendor auto-committing DDL, user-written COMMIT,
and external/nontransactional effects cannot be undone. The API's explicit `autoCommit` option
supports commands such as PostgreSQL VACUUM. Auto-commit failures can leave partial changes.
Uncertain outcomes are explicitly reported; writes are never retried
automatically. Each run gets a physical session that is discarded afterward: SET state, temp
tables and open transactions are not retained between runs or leaked into MCP agent sessions.
This adds connection-establishment cost compared with reusing a physical pooled session.

Scripts are first extracted into at most 32 exact execution units. Semicolons inside quoted
text, identifiers, nested comments, and PostgreSQL dollar quotes are preserved. Standalone SQL
Server `GO` and Oracle `/` separators create whole client batches, so procedural semicolons stay
within their originating batch. `GO n` and MySQL `DELIMITER` directives are rejected with
actionable errors. All positional parameter markers and values are validated before any unit
executes, then the flat value list is consumed in unit order. Each response reports its exact
`statements` and every JDBC result carries the producing `statementIndex`.

In transactional mode a savepoint precedes each unit. A failed unit is rolled back and the
browser displays the sanitized database error, statement number, transaction implications, and
a countdown controlled by `--dba-decision-timeout`. Continue skips that unit, Skip all similar
also skips later failures with the same SQLState/vendor code (or exception type fallback), and
Cancel rolls back the shared transaction where possible. If savepoints or rollback are unsafe,
only Cancel is enabled. Expiry, owner loss, session termination, or Script-tab closure cancels
the paused job. Completed read grids are retained with a partial/interrupted warning. Auto-commit
scripts cannot undo earlier committed units. MCP agents never receive continuation decisions.

Results show row sets, affected-row counts and commit outcomes. Result tabs are labeled
`Result 1`, `Result 2`, and so on. Each result tab has a close button that immediately releases
that retained browser result; the final result can be closed as well. Commands that do not
return JDBC rows report their outcome without creating a Data Grid tab. Each reusable Data Grid
has a compact exact-statement preview/viewer, a retained but not-yet-applied filter expression,
and placeholder clearing, order/filter, and Find/Replace controls. The SQL viewer is read-only,
non-wrapping, independently scrollable, and resizable from all edges and corners. Metadata grids
identify that source SQL is unavailable.

Data columns can be resized and reordered independently. Drag headers directly, use
Alt+Left/Alt+Right on a focused header, or draft an order in the Columns tab of Result Set
Order/Filter Settings using drag/drop or Move Up/Down controls. Duplicate labels remain distinct
through stable IDs; widths follow their columns, and each Result tab retains its own order.
The row-number corner is visually blank and fixed at the top-left, column headers stay visible
during vertical scrolling, and numbered rows stay visible during horizontal scrolling. The row
number column cannot be reordered. Wide grids scroll horizontally; long result sets remain
virtualized and scroll vertically. Up to 32 JDBC results share the
configured UI row cap and a conservative byte allowance; choose result tabs to inspect multiple
outputs. Parameters bind through PreparedStatement; no-parameter SQL uses Statement
so vendor operators remain intact. PostgreSQL cursor fetching applies to extracted statements
in non-auto-commit mode; auto-commit and multi-result client batches can buffer in the JDBC driver
outside the retained-result allowance ([pgJDBC fetching requirements](https://jdbc.postgresql.org/documentation/query/)).

Human database errors include the actual database message and SQLSTATE, capped at 8 KiB,
with saved connection credentials redacted. If redaction is unavailable, details fail closed.
Messages remain within the owning browser job, never general logs or MCP results. MCP agents
remain on the separate restricted single-SELECT, read-only transaction and object-grant path.

## Drivers and persistence

The default embedded Maven Resolver uses HTTPS Maven Central with checksum failure enforcement.
Installed Maven mode instead uses the user's settings/mirrors for metadata and JARs; it never
falls back to direct downloads. See [download configuration and diagnostics](dba-driver-downloads.md).
Native file-selection dialogs allow 90 seconds independently of query/setup deadlines. Runtime
dependency JARs are copied as a complete, atomically installed bundle under
`<dba-dir>/drivers/<bundle-id>`. Manifests record exact versions, complete paths and SHA-256
hashes. The private resolver cache is `<dba-dir>/drivers/repository`. Saved profiles remain
pinned; updates are explicit. Nothing downloads when opening `/dba` or at application startup.
No vendor licence agreement is accepted by the application.

The classpath supports up to 64 JARs / 512 MiB. Service-provider metadata discovers driver
classes; an explicit override remains possible. Snowflake 4.x uses
`net.snowflake.client.api.driver.SnowflakeDriver`, while 3.x uses the older JDBC class.
The native file picker supports multiple JARs; when unavailable, enter paths or use the
JAR-only upload fallback (128 MiB per file). Uploads remain in the application-owned driver
directory. There is no private-key upload endpoint.

Profiles migrate in place to version 2 when saved, retaining connection IDs and grants.
Known public properties and explicit pool settings go in profile JSON. Passwords and unknown
properties go into bounded chunked OS-vault records (64 KiB total; 2,400 bytes per record).
Old single-record credentials remain readable. Vault failure never falls back to plaintext.
Use password keep/replace/remove and per-property Reset. Environment placeholders must be
`${ENV_VAR_NAME}` and resolve only for operations; resolved secrets are not returned.

Pool defaults: maximum 2, minimum idle 0, acquisition 10,000 ms, validation 3,000 ms, idle
60,000 ms, lifetime 300,000 ms. Pool size overrides are limited to 16; minimum idle cannot
exceed maximum. Timeouts are validated, with a maximum of 86,400,000 ms. Global DBA job
admission remains separate. Profile edits/removal require active jobs to finish and close
the old pool/classloader. Driver-owned housekeeping/provider cleanup is version-sensitive;
retest new driver versions before operational deployment.

## Snowflake RSA key-pair authentication

Snowflake defaults to `snowflake_jwt` and uses account/hostname, username, warehouse, database,
schema and role. This is **RSA authentication, not SSH transport**. No SSH tunnels are managed.

- Select an existing encrypted or unencrypted PKCS#8 PEM RSA private key of at least 2048 bits.
- The application reads that file in place, never copies/modifies/deletes it. A native Browse
  control is provided; headless desktop environments use manual path entry, never upload.
- Validate shows format, encryption, bit length and the SHA-256 public-key fingerprint.
- PKCS#1, OpenSSH, public-only, malformed and weak/non-RSA keys are rejected; convert a copy
  externally when needed. Encrypted keys are recommended; file permissions remain your responsibility.
- The passphrase is temporary during Test and reaches the OS vault only on Save. Authentication
  uses JDBC `authenticator`, `private_key_file`, and `private_key_pwd`, never URL credentials.
  Inline keys are rejected. Very old drivers using legacy password parameter names need
  explicit vendor-version validation; the current 4.x path is the tested driver-loading target.
- Replacing key content requires retesting. The matching public key must already be registered
  for the Snowflake user. The application never rotates Snowflake user keys or changes account authentication.

References: [Snowflake key-pair authentication](https://docs.snowflake.com/en/user-guide/key-pair-auth),
[JDBC parameters](https://docs.snowflake.com/en/developer-guide/jdbc/jdbc-parameters),
[driver configuration](https://docs.snowflake.com/en/developer-guide/jdbc/jdbc-configure).

## Setup API

All routes below require the browser session and CSRF token, except bootstrap. Setup operations
return `202` with an owned job ID; poll/release `/api/dba/jobs/{id}` and cancel with POST
`/api/dba/jobs/{id}/cancel`. Draft tests and setup jobs share the DBA executor/queue/deadlines.
Cancellation is best effort for drivers/native dialogs; jobs continue to occupy admission
until the operation actually exits. There is no automatic retry of database operations.

| Route | Input / result |
|---|---|
| `POST /api/dba/bootstrap` | `{}` → automatic cookie, CSRF, settings, expiry |
| `GET /api/dba/templates` | Ordered templates and curated descriptors |
| `POST /api/dba/setup/driver-status` | `templateId, groupId, artifactId` → latest availability and verified installed bundles |
| `POST /api/dba/setup/driver-install` | Above plus exact `version` → atomic bundle; progress via job status |
| `POST /api/dba/setup/driver-inspect` | `jars:[]` → normalized paths and discovered classes |
| `POST /api/dba/setup/properties` | `templateId, driverClass, jars, url` → JDBC/catalog descriptors |
| `POST /api/dba/setup/file-select` | `kind: "jar", "key", "maven-executable", "maven-settings", "maven-cert"` → selected local paths / desktop unavailable; 90-second deadline; Maven selection returns one launcher file, never uploads or executes it |
| `GET /api/dba/settings/driver-downloads` | Effective download mode, optional executable/settings/PEM paths, TLS bypass flag and default settings path; no file contents |
| `PUT /api/dba/settings/driver-downloads` | `mode, command?, settings?, certPem?, insecureTls?`; validate and atomically persist `settings.json.driverDownloads` |
| `POST /api/dba/setup/key-validate` | `path, passphrase?` → non-secret key metadata |
| `POST /api/dba/setup/draft-test` | Full unsaved profile, optional `connectionId` to keep saved secrets, optional `confirmDriverEffects` |
| `POST /api/dba/connections` | Full profile plus temporary `receipt` or `saveUntested:true` |
| `PUT /api/dba/connections/{id}` | Same validation, preserves connection ID/grants |
| `POST /api/dba/drivers/import` | Raw `application/java-archive`, JARs only |

Descriptor cache is bounded to eight small entries, keyed by driver bytes/template/class/URL.
Metadata discovery does not connect a saved profile. Profiles/results are not graph records.
The DBA allowance is an admission/accounting allowance, **not a hard JVM/process RAM cap**;
Maven resolution, driver/native allocations and JDBC-internal buffers can exceed estimates.

## Named MCP targets and permissions

Every connection-specific DBA MCP tool requires `connectionName`, including SELECT,
EXPLAIN/plan analysis, metadata and catalog DDL reads. `connectionId` is optional; when
supplied it must match that name. Tools never infer the browser’s selected/default connection.
Obtain permitted names with `dba_list_connections`. Job status/cancellation/release remain
bound to the original owned job and do not choose or execute SQL on another connection.

Read grants now pin **both stable UUID and connection name**, plus schema/object scope.
Names are unique ignoring case, surrounding whitespace and Unicode canonical normalization.
A renamed connection requires reviewed/reissued agent grants. Reusing the old name for a
new connection cannot inherit access. Legacy UUID-only grants are bound to their existing
profile names during migration. Agent schemas and descriptions advertise the required name.

Example SELECT tool arguments:

```json
{"connectionName":"Reporting database","sql":"SELECT id FROM public.items WHERE id = ?","parameters":[42]}
```

## Validation and remaining release gates

Run the unit/HTTP/key tests with `mvn -pl code-graph-dba -am test`. Explicit download gate:

```powershell
mvn -pl code-graph-dba -am test "-Ddba.driver.integration=true" "-Dtest=DriverInstallationTest" "-Dsurefire.failIfNoSpecifiedTests=false"
powershell -NoProfile -File code-graph-dba/test-database-matrix.ps1
powershell -NoProfile -File code-graph-dba/test-browser.ps1 -NodeModules "PATH\TO\node_modules"
```

The matrix provisions PostgreSQL, MariaDB and MySQL sequentially with random loopback ports,
1 GiB container limits and tmpfs storage. It removes its ownership-labelled containers and
newly introduced images when unused, preserving pre-existing images/containers.
An explicit `-Databases oracle` run also supports Oracle Free (3 GiB limit, disposable
container storage). See [catalog tree navigation](dba-catalog-tree.md) for the implemented
per-vendor branches, lazy loading, Refresh behavior and metadata API.

Actual macOS/Linux/Windows desktop picker validation, locked-vault scenarios, real Snowflake
authentication, all vendor live-database tests, proxy/TLS interoperability, corrupt/offline
Maven simulations, expanded UI accessibility and mixed graph/DBA load remain distinct release
gates. Docker cannot certify Snowflake authentication or macOS Keychain. No paid resources or
account key changes are provisioned automatically. See [validation evidence](dba-validation.md).
